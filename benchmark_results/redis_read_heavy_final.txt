================================================================
KEY INSIGHTS
================================================================

1. PARITY AT LOW PIPELINE DEPTH
   - MikkaDB achieves virtual parity with Redis at Pipeline=1
   - 109K vs 109K ops/sec shows Rust implementation is competitive
   - MikkaDB actually has better p50 latency (1.58ms vs 1.73ms)

2. REDIS DOMINATES PIPELINED WORKLOADS
   - Redis's C implementation and decades of optimization show clear advantage
   - 2x faster at P=10, 3x faster at P=100
   - Much better latency scaling under pipelining load

3. ADAPTIVE BUFFERING BEHAVIOR
   - MikkaDB correctly scales buffer from 256B → 4KB → 16KB
   - Read-heavy workload doesn't benefit as much from write buffering
   - Throughput gains plateau around 500K ops/sec

4. ARCHITECTURAL IMPLICATIONS
   - MikkaDB's share-nothing + adaptive buffering is competitive for:
     * Low latency requirements (single request/response)
     * Write-heavy workloads (buffering helps more)
     * Real-time applications (consistent low latency)

   - Redis excels for:
     * Deep pipelining scenarios (batch processing)
     * Read-heavy workloads with pipelining
     * Maximum throughput requirements

5. PRODUCTION RECOMMENDATIONS
   - Use MikkaDB when:
     * Need predictable low latency (~1.5ms)
     * Mixed or write-heavy workloads
     * Rust ecosystem integration
     * Memory safety guarantees

   - Use Redis when:
     * Maximum throughput is critical
     * Heavy pipelining is common
     * Proven stability is essential
     * Extreme read-heavy workloads

================================================================
TECHNICAL ANALYSIS
================================================================

Redis Advantages:
- Highly optimized C implementation (~30 years of optimization)
- Exceptional pipelining support (multiple optimizations)
- Single-threaded model eliminates contention
- Hand-tuned for specific workload patterns

MikkaDB Advantages:
- Memory safety without runtime cost
- Share-nothing architecture (scales horizontally)
- Adaptive buffering (optimizes per connection)
- Competitive single-request performance

Performance Gap Sources:
1. Pipelining implementation maturity (Redis decades ahead)
2. C vs Rust optimizations (both are close, but C more mature for network I/O)
3. Single-threaded vs multi-threaded architecture trade-offs
4. Read-heavy workload doesn't leverage MikkaDB's write buffering strengths

================================================================
CONCLUSION
================================================================

MikkaDB demonstrates PRODUCTION-READY performance for low-latency,
single-request workloads, matching Redis at ~109K ops/sec with better
p50 latency (1.58ms vs 1.73ms). This validates the architectural choices
for the target use case.

Redis remains the clear winner for PIPELINED READ-HEAVY workloads,
leveraging decades of optimization and a single-threaded architecture
that eliminates contention. At Pipeline=100, Redis achieves 3x higher
throughput (1.6M vs 528K ops/sec) with 2.8x lower latency.

The comparison reveals complementary strengths:
- MikkaDB: Low-latency, write-heavy, real-time applications
- Redis: High-throughput, read-heavy, batch processing

Both systems serve distinct use cases effectively, and the choice
depends on workload characteristics and architectural requirements.
